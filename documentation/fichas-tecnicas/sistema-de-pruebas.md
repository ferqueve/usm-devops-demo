# Ficha técnica · Sistema de Pruebas

## 1. Resumen ejecutivo

UTEC Space Manager implementa una **estrategia de verificación en múltiples niveles**, organizada según el principio de la pirámide de pruebas propuesto por Mike Cohn. La estrategia distribuye el esfuerzo de validación entre pruebas unitarias, pruebas de integración y pruebas extremo a extremo, asignando a cada nivel la responsabilidad que mejor desempeña: las unitarias verifican la corrección puntual de funciones y reglas de negocio aisladas, las de integración validan el cableado entre capas y los contratos internos del sistema, y las extremo a extremo confirman que los flujos críticos del usuario funcionan sobre el sistema real.

La elección de mantener los tres niveles —en lugar de concentrar el esfuerzo solamente en pruebas extremo a extremo, que son las únicas que ejercitan al sistema completo— responde a tres consideraciones técnicas. Primero, la velocidad del ciclo de retroalimentación: un cambio puntual en una función pura puede validarse en milisegundos a nivel unitario, mientras que una prueba extremo a extremo equivalente requiere arrancar la aplicación completa. Segundo, la economía de la cobertura: los casos de borde (fechas inválidas, formatos extremos, ramas condicionales raras) son inviables de cubrir con pruebas extremo a extremo pero triviales con unitarias. Tercero, la facilidad de diagnóstico: cuando una prueba unitaria falla, el origen del defecto está aislado a una unidad pequeña; cuando una prueba extremo a extremo falla, el defecto puede estar en cualquier punto de la cadena.

El sistema cuenta con los tres niveles operativos. Las pruebas unitarias y de integración cubren tanto el componente backend (Java + Spring Boot) como el componente frontend (React + TypeScript). Las pruebas extremo a extremo se implementan con Playwright sobre Chromium real, una base PostgreSQL dedicada al perfil de prueba y un mecanismo de siembra de datos que garantiza un estado conocido en cada corrida.

## 2. Cómo se usa

En el contexto de esta ficha técnica, la sección describe cómo el sistema de pruebas se integra al ciclo de desarrollo, no la operativa de comandos puntuales (esa información, por ser operacional, vive en el manual de instalación).

Las pruebas se ejecutan automáticamente como parte del proceso de integración continua definido en `.github/workflows/build.yml`. Cada vez que se sube un cambio al repositorio, el pipeline compila el backend, ejecuta toda la suite de pruebas unitarias y de integración del backend, genera el reporte de cobertura con JaCoCo, instala las dependencias del frontend, ejecuta la suite de pruebas unitarias del frontend con su reporte de cobertura, construye el bundle de producción y, finalmente, envía los reportes a SonarQube para análisis estático. Si cualquiera de estas etapas falla, el cambio queda marcado como rechazado y no se considera apto para mergear.

Durante el desarrollo local, los tests se ejecutan en modo de observación o de forma puntual mientras se itera sobre una funcionalidad. Las pruebas unitarias del frontend permiten una iteración especialmente rápida porque corren en jsdom y no requieren que la aplicación esté levantada; las del backend levantan un contexto Spring liviano sobre H2 en memoria, lo que mantiene su tiempo de ejecución por debajo del minuto. Las pruebas de integración del frontend, al utilizar Mock Service Worker para interceptar las llamadas HTTP, tampoco requieren que el backend esté corriendo.

Las pruebas extremo a extremo, por su naturaleza, requieren la pila completa funcionando. Para evitar fricción, un script orquestador (`scripts/e2e.sh`) levanta automáticamente la base PostgreSQL dedicada, el servicio Redis, el backend con perfil `e2e` y el frontend con Vite, espera los healthchecks, ejecuta Playwright y libera todos los recursos al terminar, incluso si las pruebas fallan. La estrategia de integración continua para este nivel se contempla como un workflow separado disparado en push a la rama principal y bajo programación nocturna, evitando alentar el ciclo de pull request con la ejecución completa del sistema.

## 3. Detalle técnico

### 3.1 Pruebas unitarias del backend

Las pruebas unitarias del backend se implementan con **JUnit 5** como framework de ejecución y **Mockito 5** como biblioteca de doblado de objetos. El criterio de unitariedad seguido en este proyecto considera como unidad a cada servicio (`Service`) tomado en aislamiento, mockeando todas sus dependencias —repositorios JPA, otros servicios, clientes externos— mediante anotaciones `@Mock` y la extensión `MockitoExtension`. Esta elección se fundamenta en que la lógica de negocio del sistema reside mayoritariamente en la capa de servicios, mientras que repositorios y controladores son delgados y poco aptos para ser ejercitados sin contexto.

Cada test verifica una regla de negocio o una rama condicional específica del servicio bajo prueba: por ejemplo, que el cálculo de conflictos horarios en `ReservaService` rechaza correctamente un rango solapado, o que el algoritmo de puntaje de `RecomendacionReservaService` pondera el historial del usuario según el peso configurado. La estructura del directorio `backend/src/test/java/com/utec/backend/service/` espeja la del código productivo: para cada servicio existe al menos un archivo de prueba homónimo, y servicios con alta complejidad cuentan con múltiples archivos especializados (por ejemplo `ReservaService` se descompone en cuatro archivos: el caso base, el extendido, el flujo y la lógica de recurrencias).

El conjunto cubre los servicios de reserva, recomendación —en sus cinco variantes especializadas más el orquestador y el componente programado—, inventario, espacio, edificio, tipos de elemento y de espacio, carrera, usuario, autenticación, correo electrónico, integración con Gmail, almacenamiento de archivos, estadísticas, auditoría, permisos, autenticación OAuth2, JWT, detalles de usuario, configuración de usuario, ítems solicitados en reservas, recordatorios y rastreo de actividad. Adicionalmente se prueba la utilidad de roles y el servicio JWT en aislamiento.

### 3.2 Pruebas de integración del backend

Las pruebas de integración del backend se implementan sobre el subsistema de testing de **Spring Boot**, utilizando las anotaciones `@SpringBootTest` para levantar el contexto de Spring y `@AutoConfigureMockMvc` para inyectar una instancia de `MockMvc` con la cual ejercitar la capa HTTP. Los servicios consumidos por los controladores se sustituyen mediante `@MockitoBean`, lo cual permite enfocar la prueba en la capa web sin depender de la base de datos.

A diferencia de las pruebas unitarias, estas pruebas ejercitan componentes reales del framework: la cadena de filtros de seguridad (`SecurityFilterChain`), la validación de tokens JWT, las anotaciones de autorización a nivel de método (`@PreAuthorize`), la validación declarativa de DTOs con `@Valid`, la deserialización de Jackson y el manejo centralizado de excepciones a través de `@ControllerAdvice`. Su valor radica en detectar defectos de cableado que las pruebas unitarias no pueden ver: rutas mal definidas, métodos HTTP incorrectos, restricciones de autorización inconsistentes, errores de mapeo entre DTOs y entidades, o respuestas con códigos de estado incorrectos.

Los controladores cubiertos son los de autenticación, auditoría, carrera, edificio, espacio, subida de archivos, ítem de inventario, OAuth2, recomendación, reserva (en su versión base y extendida), ítems solicitados de reserva, estadísticas, tipo de elemento, tipo de espacio, usuario y configuración de usuario.

El perfil `test` activado durante la ejecución utiliza una base de datos H2 en memoria configurada en modo de compatibilidad PostgreSQL, lo cual permite que las consultas escritas en JPQL y los métodos derivados de Spring Data se comporten de forma similar a producción sin requerir una base relacional levantada externamente. Liquibase se desactiva en este perfil porque las pruebas de controlador no acceden directamente al esquema; el modo `create-drop` de Hibernate genera la estructura a partir de las anotaciones JPA.

### 3.3 Pruebas unitarias del frontend

Las pruebas unitarias del frontend utilizan **Vitest 4** como ejecutor, **Testing Library** para la consulta del DOM y **`@testing-library/user-event`** para simular interacciones del usuario. El entorno de ejecución es **jsdom**, una implementación de DOM en JavaScript puro que permite renderizar componentes React sin un navegador real.

La organización del directorio `frontend/tests/` espeja la estructura de `frontend/src/`, agrupando las pruebas por capa funcional. La capa `lib/api/` contiene las pruebas de los clientes HTTP de cada recurso del backend, donde cada test verifica la URL construida, los encabezados enviados (incluyendo el token de autorización), la serialización del cuerpo de la solicitud, el manejo de respuestas exitosas y de errores HTTP, y la transformación de datos antes de retornarlos. La capa `lib/utils/` cubre las utilidades puras del frontend: formateadores, helpers de fecha y zona horaria, exportación a CSV, escape de cadenas. La capa `lib/config/` valida los mapas de permisos por rol y las constantes de aplicación. La capa `hooks/` ejercita los hooks personalizados que encapsulan estados asíncronos: estados de carga, manejo de errores, recarga manual, efectos colaterales sobre el almacenamiento local. Finalmente, la capa `components/` contiene pruebas de componentes de feature, verificando renderizado condicional, interacciones básicas y ramas según props.

Las convenciones adoptadas para la suite priorizan la mantenibilidad. Las consultas al DOM se realizan a través de roles ARIA y etiquetas accesibles antes que por identificadores de prueba (`data-testid`), lo que produce pruebas que se rompen ante cambios visibles para el usuario y no ante refactorizaciones internas. Toda interacción se ejecuta a través de `userEvent`, que simula la cadena completa de eventos del navegador, en contraposición a `fireEvent`, que dispara eventos sintéticos y deja escapar errores como botones deshabilitados o pointer-events bloqueados. Las esperas se resuelven con consultas `findBy*` que internamente realizan polling con tiempo de espera, evitando la introducción de pausas explícitas. La política de cero supresores —no se utilizan `as any`, `@ts-ignore` ni `eslint-disable`— obliga a corregir errores de tipo correctamente en lugar de ocultarlos.

### 3.4 Pruebas de integración del frontend

Las pruebas de integración del frontend extienden el stack de pruebas unitarias agregando **Mock Service Worker (MSW) 2** como interceptor de la red. Esta adición permite que cada prueba renderice una página real de la aplicación, completa con su `AuthProvider`, su `MemoryRouter` y su sistema de notificaciones, mientras MSW intercepta de forma transparente todas las llamadas `fetch` al backend y responde con datos estructurados según los DTO reales del servidor.

Esta arquitectura de prueba es deliberadamente diferente de las pruebas unitarias. Mientras una prueba unitaria de un componente lo monta aislado y le inyecta props, una prueba de integración monta la aplicación a través de su sistema de rutas, ejercita la composición real de contextos —autenticación, navegación, notificaciones— y valida que las llamadas a la red se construyan, despachen e interpreten correctamente. El criterio para colocar una prueba en este nivel es que el flujo bajo verificación involucre al menos dos capas funcionales del frontend que se comunican entre sí.

La infraestructura de la suite se compone de tres elementos. El helper `renderApp` recibe un conjunto de rutas declarado por cada prueba —incluyendo destinos de redirección expresados como stubs simples— y monta el árbol con los providers necesarios. El helper `loginAs` siembra el almacenamiento local con un usuario de un rol determinado para que las rutas protegidas por `RoleProtectedRoute` o `useAuth` rendericen sin requerir el flujo completo de inicio de sesión. Los handlers de MSW se organizan por recurso, exponen un comportamiento por defecto correspondiente al camino feliz, y cada prueba puede sobrescribirlos individualmente para forzar respuestas con códigos de error o cuerpos vacíos. Las fábricas (`makeUser`, `makeReserva`, `makeEspacio`, `makeInventoryItem`) producen datos de prueba consistentes que aceptan sobrescritura parcial.

La cobertura actual de este nivel comprende dieciocho pruebas distribuidas entre el flujo de autenticación —incluyendo inicio de sesión exitoso y fallido, registro con email duplicado, recuperación de contraseña, restablecimiento con tokens válidos e inválidos y cierre de sesión automático ante un código 401—, los componentes de control de permisos, la auditoría, la gestión de usuarios y los listados de inventario y de espacios.

### 3.5 Pruebas extremo a extremo

El nivel extremo a extremo se implementa con **Playwright** como ejecutor sobre **Chromium** real, una base **PostgreSQL** dedicada y un mecanismo de siembra de datos activado por perfil Spring. La elección de Playwright sobre alternativas como Cypress se fundamenta en su soporte nativo para múltiples navegadores, su modelo de espera automática que reduce la flakiness, y su capacidad de generar trazas y videos para diagnóstico de fallas.

La motivación para introducir este nivel surge de las limitaciones inherentes a jsdom como entorno de pruebas. Componentes que dependen de la primitiva `pointer-events` —notablemente los `Select` de Radix UI utilizados en varios formularios— no funcionan en jsdom porque dicha primitiva no está implementada. Componentes que dependen de cálculos de layout, como las gráficas de `recharts` en estadísticas y dashboard, tampoco renderizan significativamente. Estos componentes solo pueden validarse en un navegador real.

La infraestructura del nivel se compone de cinco piezas. Un perfil Spring `e2e` (`backend/src/main/resources/application-e2e.properties`) configura Postgres real en lugar de H2 para garantizar fidelidad con producción en tipos como `JSONB` y `timestamptz`, mantiene Liquibase activo —ejercitando así los changesets reales— y deshabilita los servicios externos no objeto de la prueba (correo Gmail, almacenamiento MinIO, autenticación OAuth2 con Google). Un `E2EDataSeeder` (`backend/.../e2e/E2EDataSeeder.java`) anotado con `@Profile("e2e")` y `CommandLineRunner` siembra de forma idempotente un usuario por rol, un edificio, un tipo de espacio, dos espacios, un tipo de elemento, un ítem de inventario, una carrera, tres reservas con horarios deterministas en zona horaria local de Montevideo —dos pendientes con analista asignado a las 10:00 y a las 14:00, y una aprobada a las 18:00 del día siguiente— y una solicitud de inventario pendiente asociada a la reserva aprobada. El uso de horarios fijos por reloj —en lugar de horarios relativos al momento del arranque del backend— hace estables los tests que dependen de bloqueos de horas en el formulario. Una clase `E2ECacheConfig` registra un `NoOpCacheManager` con calificador `@Primary`, sustituyendo al cache Redis del perfil normal: las pruebas E2E necesitan leer siempre el estado real de la base. Un `docker-compose.e2e.yml` levanta Postgres y Redis dedicados en puertos no estándar (5433 y 6380) para no interferir con los entornos de desarrollo. Finalmente, un script orquestador `scripts/e2e.sh` levanta los servicios, espera sus healthchecks, arranca backend y frontend, ejecuta Playwright y libera todos los recursos al finalizar, incluso ante fallo.

Los flujos cubiertos por la suite extremo a extremo son los críticos para el negocio. En el área de autenticación se valida el inicio de sesión exitoso del administrador con redirección al dashboard, el rechazo del inicio de sesión con credenciales inválidas y la persistencia del mensaje de error, y el cierre de sesión desde el panel lateral con la consiguiente limpieza del almacenamiento local. En el área de reservas se ejercitan la creación de una nueva reserva por parte de un docente recorriendo el formulario completo —espacio, título, carrera, analista, fecha y horas—, la creación incluyendo un ítem solicitado al pedido, la creación con recurrencia semanal y verificación de las múltiples instancias generadas, la cancelación por parte del dueño de una reserva aprobada desde la vista de tarjetas, la aprobación por parte del administrador de una reserva pendiente con confirmación, el rechazo por parte del administrador de una reserva pendiente con redacción del motivo en el cuadro de diálogo, y la prevención por parte del formulario de elegir horas que solapan con reservas ya aprobadas. Adicionalmente se valida la carga de la vista calendario, el cambio a la vista tabular y la aplicación del filtro de estado sobre el listado. En el área de inventario se cubre el ciclo completo de gestión de una solicitud por parte del administrador: apertura del cuadro de diálogo de gestión, asignación de un ítem físico al pedido, aprobación de la solicitud y posterior marcado como entregada. Finalmente, en el área de permisos se valida que un estudiante que intenta acceder a una ruta administrativa restringida es redirigido por `RoleProtectedRoute` a su ruta inicial permitida.

Durante la implementación de este nivel se detectaron y corrigieron dos defectos reales en el código de producción que las pruebas unitarias y de integración no habían capturado. El primero fue una importación faltante de `useCallback` en `ReservationCalendarView.tsx`, que provocaba el crash silencioso del componente cuando un usuario sin error boundary entraba a `/reservations`; las pruebas unitarias no lo detectaron porque ese componente no se monta en aislamiento, y las de integración no lo cubrían por la limitación de Radix Select en jsdom. El segundo fue una incompatibilidad entre el tipo `LoginResponse` del frontend, que esperaba un campo `id`, y el DTO `AuthenticationResponse` del backend, que envía `userId`. Esto provocaba que el identificador del usuario quedara como `undefined` tras el inicio de sesión, rompiendo silenciosamente cualquier filtro frontend basado en `user.id` —notablemente el panel de reservas pendientes del analista, que comparaba `reserva.analistaId === user.id` y siempre evaluaba a falso. Ambos defectos se hallaron porque las pruebas extremo a extremo ejercitan la cadena real de tipos y datos.

## 4. Métricas y evidencia

La suite de pruebas del backend cuenta con cincuenta y cuatro archivos que totalizan aproximadamente seiscientos casos de prueba, distribuidos entre treinta y tres archivos de pruebas unitarias de servicios y dieciocho archivos de pruebas de integración de controladores, más archivos auxiliares de utilidades, configuración y seguridad. La ejecución completa toma entre veinte y treinta segundos. La cobertura medida con JaCoCo, registrada en la ficha `analisis-de-codigo.md`, se sitúa aproximadamente en el cincuenta por ciento de líneas y se concentra en las capas de servicio y de controlador, donde reside la lógica de negocio relevante.

La suite de pruebas unitarias del frontend cuenta con noventa y siete archivos que totalizan quinientos veintidós casos de prueba, ejecutados en aproximadamente cincuenta segundos. La cobertura medida con el proveedor v8 de Vitest se sitúa en treinta y tres coma trece por ciento de líneas. Esta cobertura se concentra deliberadamente en las capas con valor de prueba real —clientes HTTP, utilidades puras, hooks de estado y componentes con ramas condicionales— excluyendo por configuración los componentes UI primitivos (envoltorios de Radix sin lógica propia), los layouts de presentación y los archivos de barrel export.

La suite de pruebas de integración del frontend cuenta con trece archivos que totalizan dieciocho casos de prueba, ejecutados en aproximadamente treinta y dos segundos sobre Vitest con jsdom y MSW.

La suite de pruebas extremo a extremo cuenta con noventa y siete archivos que totalizan cien casos activos de prueba, sobre Chromium real (con zona horaria fijada en `America/Montevideo` para que las fechas generadas en JS coincidan con las del seeder), ejecutados en aproximadamente siete minutos una vez que los servicios están levantados (la inicialización completa de Postgres, Redis, backend con perfil `e2e` y Vite suma en torno a un minuto adicional). Cubre los flujos críticos de autenticación, ciclo de vida completo de reservas en sus diversas modalidades, filtros y paginación del listado, control de acceso por rol, visibilidad pública vs privada, interacción con el calendario, persistencia del diálogo de detalles, CRUD completo de ítems de inventario, acciones masivas con confirmación, asignación y desasignación a espacios, gestión de tipos de elemento, filtros del panel de solicitudes, flujo de aprobación/rechazo, CRUD de espacios con cambio de estado, búsqueda y filtros por capacidad, vista detalle con gestión de inventario asociado, sistema de recomendaciones cubriendo espacios, horarios, ítems y analistas sugeridos en el formulario de reserva, panel de prioritarias en el dashboard del analista, panel de mantenimiento, administración de usuarios con búsqueda, filtros, edición, cambio de rol, activar/desactivar, estadísticas y gestión de carreras, y consulta de logs de auditoría con filtros y diálogo de detalles para el admin, todos descritos en §3.5.

La calidad estática del código se evalúa adicionalmente mediante **SonarQube** sobre un Quality Gate denominado `USM Strict`, configurado con condiciones agresivas de cobertura, duplicación, hotspots de seguridad revisados y calificaciones máximas de mantenibilidad, confiabilidad y seguridad. El proyecto aprueba todas las condiciones del gate excepto la cobertura global, situación documentada como decisión consciente en la ficha `analisis-de-codigo.md`: el umbral del ochenta por ciento se mantiene como estándar máximo aspiracional y la cobertura efectiva del proyecto se considera adecuada para su naturaleza académica.

## 5. Riesgos, limitaciones y trabajo futuro

La estrategia de pruebas presenta tres limitaciones reconocidas que delimitan su alcance actual.

La primera es la imposibilidad de cubrir desde jsdom los componentes del frontend que dependen de primitivas no implementadas en ese entorno. Los formularios construidos con `@radix-ui/react-select` —presentes en la creación de reservas, en la edición de espacios, en el cambio de rol de usuario y en la solicitud de inventario— no abren su menú desplegable en jsdom debido a la ausencia de `pointer-events`. Las visualizaciones construidas con `recharts` no producen un layout significativo en jsdom. Estas limitaciones técnicas son la principal motivación que llevó a introducir el nivel de pruebas extremo a extremo, donde un navegador real sí soporta esas primitivas. Polifillar las características en jsdom sería una alternativa más rápida pero genera pruebas que validan una versión simulada del DOM, aumentando el riesgo de falsos positivos sin agregar valor de validación.

La segunda es la ausencia de pruebas específicas para la capa de persistencia del backend. Las consultas no triviales —como la detección de reservas conflictivas o la búsqueda de reservas pendientes por usuario— no se prueban contra una base real, sino indirectamente a través de los tests de servicio donde el repositorio se mockea. Las migraciones Liquibase sí se ejercitan al arrancar el backend con perfil `e2e` (que las aplica en orden sobre una base limpia), pero no existe una prueba dedicada que valide los changesets en aislamiento. El trabajo futuro contempla incorporar pruebas con `@DataJpaTest` sobre H2 en modo PostgreSQL para los repositorios de mayor complejidad, y eventualmente Testcontainers con Postgres real para verificar el flujo completo de migraciones.

La tercera es la cobertura aún parcial del nivel extremo a extremo. La suite actual contiene los flujos críticos del negocio en autenticación, en el ciclo de vida completo de una reserva (creación con o sin ítems, recurrencia, aprobación, rechazo y cancelación), en la prevención de conflictos de horario, en las distintas vistas del listado, en la gestión completa de solicitudes de inventario y en el bloqueo de rutas por rol. Quedan fuera escenarios deseables como el restablecimiento de contraseña con interacción de correo electrónico, la edición del rol de un usuario por parte del administrador, las operaciones de creación, edición y eliminación de espacios y de ítems de inventario, las visualizaciones de estadísticas con `recharts` y los flujos de auditoría. La edición de una reserva pendiente queda formalmente saltada con `test.skip` porque, aunque el endpoint backend está disponible, no existe UI que lo invoque. Algunos de los escenarios pendientes requieren intercambios reales con servicios externos —notablemente el reset de contraseña depende del envío real de un correo— y otros simplemente se incorporarán en iteraciones posteriores a medida que se priorice cada uno frente al costo de mantenimiento que suman a la suite.

Adicionalmente, se mantiene como mejora deseable la incorporación de un test de pila completa puramente backend —una prueba con `@SpringBootTest(webEnvironment = RANDOM_PORT)` y `TestRestTemplate` que ejercite el ciclo completo registro, inicio de sesión, creación de reserva y consulta— que validaría el flujo de servidor sin requerir el frontend.
